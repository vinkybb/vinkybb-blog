# AgentRx：AI Agent 失败诊断的系统化框架

随着 AI Agent 从简单的对话机器人演变为能够自主处理云端运维事件、操作复杂 Web 界面、执行多步骤 API 工作流的智能系统，一个新挑战浮出水面：透明性。当人类犯错时，我们通常能够追溯其逻辑脉络；但当 AI Agent 失败——或许是虚构工具输出，或是在五十步任务的第十步偏离安全策略——精准定位"何处出错、为何出错"变成了一场艰巨的手工排查。

微软研究院推出的 AgentRx 框架，正是为解决这一痛点而生。这是一个自动化、领域无关的诊断系统，能够精准识别 Agent 执行轨迹中的"关键失败步骤"。

## 核心问题：AI Agent 调试的三大难点

现代 AI Agent 具有三个显著特征，使其调试难度远超传统软件：

首先是**长时程执行**。Agent 可能执行数十个动作，跨越长时间周期，执行轨迹呈现长链条结构。其次是**概率性输出**。相同输入可能产生不同输出，复现失败变得极为困难。最后是**多 Agent 协作**。失败可能在多个 Agent 之间传递，原始根因被层层掩盖。

传统的成功指标（如"任务是否完成"）无法揭示深层问题。要构建安全可靠的 Agent，我们需要识别轨迹变为不可恢复的确切时刻，并捕获该步骤的错误证据。

## 四阶段诊断管道：从混沌日志到精准定位

AgentRx 将 Agent 执行视为需要验证的系统轨迹，摒弃依赖单一 LLM"猜测"错误的方式，转而采用结构化的多阶段管道：

**第一阶段：轨迹标准化**。不同领域的异构日志被转换为统一的中间表示，消除格式差异带来的诊断障碍。

**第二阶段：约束合成**。框架基于工具 Schema（如"API 必须返回有效 JSON 响应"）和域策略（如"删除数据前需用户确认"）自动生成可执行的约束条件。这些约束具有明确的触发条件，只在适用时才进行检查。

**第三阶段：受保护评估**。AgentRx 逐步评估约束，为每个违规生成带证据支撑的验证日志。这种"审计式"方法确保每一步诊断都有据可查。

**第四阶段：LLM 评判**。最终，一个 LLM 评判器基于验证日志和标准化的失败分类体系，识别首个不可恢复错误——即关键失败步骤。

这种管道式设计的关键优势在于：前三个阶段全部基于可执行规则，不依赖 LLM 的不确定性；仅在最终评判阶段引入 LLM，且其决策基于前序阶段生成的结构化证据，大幅提升了诊断的可信度。

## 九类失败分类：跨领域通用的诊断语言

为支撑诊断评估，研究团队发布了 AgentRx Benchmark，包含 115 条手动标注的失败轨迹，覆盖三个复杂领域：τ-bench（结构化 API 工作流）、Flash（真实运维事件管理）、Magentic-One（通用多 Agent 系统）。

基于扎根理论方法，研究团队建立了九类失败分类体系：

- **计划遵守失败**：忽略必要步骤或执行未规划的额外动作
- **信息虚构**：篡改未基于轨迹或工具输出的事实
- **无效调用**：工具调用格式错误、缺失参数或违反 Schema
- **输出误读**：错误理解工具输出，基于错误假设行动
- **意图-计划错位**：误解用户目标或约束，规划方向错误
- **用户意图不明确**：因必要信息缺失无法继续执行
- **意图不支持**：现有工具无法完成请求任务
- **安全护栏触发**：执行被安全或访问限制阻断
- **系统故障**：连接性或工具端点失效

这套分类体系揭示了核心洞察：在多 Agent 系统（如 Magentic-One）中，轨迹往往包含多个错误，但关键在于识别首个不可恢复的失败节点，而非淹没在后续连锁错误中。

## 关键成果：显著超越提示基线

实验结果显示，AgentRx 相比现有 LLM 提示基线取得显著提升：

- 失败定位准确率绝对提升 **23.6%**
- 根因归因准确率提升 **22.9%**

通过提供失败背后的"证据链"，AgentRx 让开发者超越试错式调试，转向系统化的工程化方法。这种从"猜测"到"验证"的转变，标志着 Agent 开发从实验阶段迈向工程化阶段。

## 开源意义：构建可审计的 Agent 生态

Agent 可靠性是现实部署的前提条件。微软研究院开源 AgentRx 框架及完整标注数据集，邀请研究者和开发者诊断自身的 Agent 工作流，并贡献失败约束库。

这种开放姿态传递出深层信号：Agent 技术要真正落地，需要社区共同建立诊断语言、验证标准和工程范式。当 Agent 的每一步执行都可追溯、每一处失败都可归因，我们才能构建不仅强大，而且值得信任的 AI 系统。
